## Prioridad 1: Tests de integración reales

### Diagnóstico

El archivo `src/modules/shared/domain/multi-tenant-isolation.test.ts` (y probablemente otros del mismo estilo) prueban funciones inventadas dentro del propio test, no el código de producción:

```ts

  return store.find((item) => item.id === resourceId && item.tenantId === tenantId) || null;
```

Un test así da verde siempre, sin importar si mañana alguien rompe el filtro de `tenantId` en `stock/actions.ts`. Hay que reemplazar/complementar esto con tests que ejecuten las Server Actions reales contra una base de datos real.

**Criterio de aceptación:** `npm run test:db:up && npm run test:integration && npm run test:db:down` corre de punta a punta en una máquina limpia (o en CI) sin intervención manual.

> **Nota técnica importante:** las Server Actions actuales leen la cookie con `cookies()` de `next/headers`, que depende del request context de Next.js y no se puede invocar así nomás desde un test de Vitest plano. Hay dos caminos, a elegir por quien lo implemente:

### 2.2 — Helper central de permisos

Crear `src/modules/shared/infrastructure/permissions.ts`:

```ts
import { TenantContext, UserRole } from "../domain/tenant";

export class ForbiddenError extends Error {
  constructor(message: string = "No tenés permiso para realizar esta acción") {
    super(message);
    this.name = "ForbiddenError";
  }
}

/**
 * Verifica que el rol del contexto esté entre los roles permitidos.
 * Lanza ForbiddenError (no un string genérico) si no cumple.
 */
export function assertRole(context: TenantContext, allowedRoles: UserRole[]): void {
  if (!allowedRoles.includes(context.role)) {
    throw new ForbiddenError(
      `Esta acción requiere uno de estos roles: ${allowedRoles.join(", ")}. Tu rol actual es ${context.role}.`
    );
  }
}

/**
 * Casos con reglas más finas que un simple allowlist de roles
 * (ej: un ADMIN puede crear usuarios pero no OWNERs).
 */
export function assertCanAssignRole(context: TenantContext, targetRole: UserRole): void {
  if (context.role === "ADMIN" && targetRole === "OWNER") {
    throw new ForbiddenError("Un ADMIN no puede crear ni ascender a otro usuario a OWNER");
  }
  if (context.role === "STAFF") {
    throw new ForbiddenError("Un STAFF no puede gestionar usuarios");
  }
}
```

Esta lógica de `assertCanAssignRole` ya existe duplicada en `user-service.ts` y `onboarding-service.ts` — al centralizarla acá, se elimina esa duplicación.

### 3.1 — Aplicar los límites de plan que ya están definidos y no se usan

`PLAN_LIMITS_MAP` (en `subscription-policy.ts`) define `maxBranches`, `maxStaff` y `maxAppointmentsPerMonth`, pero ninguna Action los consulta. Agregar en `createBranchAction` y `createUserAction`:

```ts
import { PLAN_LIMITS_MAP } from "@/modules/subscriptions/domain/subscription-policy";

export async function createBranchAction(input: CreateBranchInput) {
  // ... auth y rol ya verificados arriba
  const tenant = await db.tenant.findUnique({ where: { id: context.tenantId }, select: { plan: true } });
  const limits = PLAN_LIMITS_MAP[tenant?.plan ?? "STARTER"];

  if (currentBranchCount >= limits.maxBranches) {
    throw new Error(
      `Tu plan ${limits.name} permite hasta ${limits.maxBranches} sucursal(es). Mejorá tu plan para agregar más.`
    );
  }
  // ... resto de la lógica
}
```

Mismo patrón para `maxStaff` en `createUserAction`, y para `maxAppointmentsPerMonth` en `createPublicBookingAction` (contando turnos del mes actual).

### 3.2 — Unificar y corregir el contador de trial

Elegir **una sola** duración de trial (recomendado: 14 días, ya que es lo que se usa en el flujo principal de registro) y:

1. En `subscriptions/actions.ts`, cambiar el `30 * 24 * 60 * 60 * 1000` a `14 * ...` para que coincida con `prisma-onboarding-repository.ts`.
2. En `(dashboard)/layout.tsx`, dejar de reconstruir "días transcurridos" restando desde un número fijo. Calcular directo desde la fecha real:

```ts
getTenantSubscriptionAction().then((res) => {
  if (res.success && res.subscription?.trialEndsAt) {
    const trialEndsAt = new Date(res.subscription.trialEndsAt).getTime();
    const graceEndsAt = trialEndsAt + 7 * 24 * 60 * 60 * 1000;
    const now = Date.now();
    setIsGracePeriod(now > trialEndsAt && now <= graceEndsAt);
    setIsBlackout(now > graceEndsAt);
    setDaysIntoGrace(Math.max(0, Math.ceil((now - trialEndsAt) / (1000 * 60 * 60 * 24))));
  }
});
```

Esto elimina la clase entera de bug (contador que se planchea en un tope y nunca cruza el umbral), porque ya no depende de reconstruir "cuántos días pasaron" a partir de "cuántos quedan": compara fechas reales directamente.

### 3.3 — Mover la idempotencia del webhook de Mercado Pago a la base de datos

`processedWebhookEvents` sigue siendo un `Set` en memoria (`mercadopago-webhook.ts`). En Vercel (serverless), distintas invocaciones pueden correr en instancias distintas y no comparten memoria — un mismo evento reenviado por Mercado Pago podría procesarse más de una vez.

Agregar una tabla (o reusar una columna existente) para persistir esto:

```prisma
model ProcessedWebhookEvent {
  id        String   @id @default(uuid())
  eventKey  String   @unique
  createdAt DateTime @default(now())
}
```

Y en el webhook, reemplazar el chequeo del `Set` por una consulta/insert con manejo de la violación de unicidad como señal de "ya procesado":

```ts
try {
  await db.processedWebhookEvent.create({ data: { eventKey } });
} catch (err) {
  // Violación de unique constraint = evento duplicado, no es un error real
  return NextResponse.json({ success: true, message: "Evento ya procesado (Idempotente)" });
}
```

### 3.4 — Rate limiter: mismo problema de memoria en serverless

`rate-limiter.ts` usa un `Map` en memoria — funciona bien en un servidor tradicional siempre encendido, pero en Vercel cada instancia tiene su propia memoria, así que el límite real efectivo es "N por instancia", no "N en total". Para el volumen inicial (pocos negocios, piloto) esto puede no ser crítico, pero antes de una campaña de marketing o crecimiento real, migrar a un store compartido:

- Opción simple: Vercel KV o Upstash Redis (ambos con SDKs que funcionan bien en Edge/Serverless).
- Mantener la misma interfaz (`checkRateLimit(key, max, windowMs)`) para no tener que tocar el código que ya la llama, solo cambiar la implementación interna.

### 3.5 — Conectar el servicio de auditoría que ya existe pero no se usa

`src/modules/shared/domain/audit-service.ts` está escrito pero no se llama desde ningún lado del código de producción. Para un sistema que maneja facturación y datos fiscales, tener trazabilidad de "quién hizo qué y cuándo" importa (y probablemente lo vas a necesitar si алguna vez hay un reclamo o una auditoría real de ARCA).

Conectarlo como mínimo en:
- Cambios de configuración fiscal (`saveAfipConfigAction`)
- Emisión y anulación de comprobantes
- Cambios de rol de usuario y creación/borrado de usuarios
- Cambios de plan de suscripción

### 3.6 — Runbook de incidentes básico

No es código, pero para un 10/10 operativo real hace falta un documento corto (`docs/RUNBOOK.md`) con: qué hacer si `/api/health` da 503, cómo rotar `JWT_SECRET` sin tirar abajo todas las sesiones activas sin avisar, cómo restaurar un backup de Supabase, y a quién contactar si Mercado Pago reporta un pago no reflejado.

---

## Resumen: orden de ejecución sugerido

1. **Infraestructura de tests de integración** (1.1–1.2) — sin esto, nada de lo demás se puede probar de verdad.
2. **Matriz de permisos acordada con vos** (2.1) — es una decisión de negocio, bloquea el resto de la Prioridad 2.
3. **Helper de permisos + aplicarlo en los 4 módulos que faltan** (2.2–2.3).
4. **Tests de integración de aislamiento y de permisos** (1.3, 2.4) — en paralelo, ya con la infraestructura lista.
5. **CI/CD** (1.6) — para que lo anterior no dependa de la memoria de nadie.
6. **Límites de plan + contador de trial + idempotencia del webhook** (3.1–3.3) — cierran los huecos de negocio que quedaron sueltos.
7. **Rate limiter persistente y auditoría conectada** (3.4–3.5) — antes de escalar más allá del piloto.

```
orden de la sección "Resumen: orden de ejecución sugerido", un punto a
la vez.

Antes de escribir código para el punto 2 (matriz de permisos), mostrame
la tabla propuesta en la sección 2.1 y esperá mi confirmación o mis
cambios — es una decisión de negocio mía, no tuya.

Para cada punto:
- Mostrame el archivo completo modificado, no solo un diff parcial.
- Corré la suite de tests correspondiente y pegame la salida real.
- Si agregaste un test nuevo, mostrame que ese test falla si revertís
  el fix a propósito (así confirmamos que el test realmente prueba algo
  y no es otro caso de "test de mentira").
```
